# Decisions

One entry per decision: **date — what** — why.

- **2026-10-09 — Checkpoint runs `git pull --rebase --autostash` before pushing; on conflict it aborts and leaves the commits local** — a bot or another machine pushing otherwise made every checkpoint push fail silently. The conflict is written to the gitignored `.claude/.last_checkpoint_sync_problem` and shown at session start; nothing is ever forced.
- **2026-10-09 — Review rule applies to finished features and milestones, not checkpoint pushes** — checkpoints are backups; reviewing each one would stall the session for no benefit.
- **2026-10-09 — The checkpoint note covers every sync failure, not only rebase conflicts** — a failed pull (offline, autostash-pop conflict), a rejected push and a repo left mid-rebase all leave the commits local and are written to `.claude/.last_checkpoint_sync_problem`; a clean checkpoint removes the note. Tested against a local bare remote (conflict, unreachable remote, pre-receive rejection, mid-rebase).
- **2026-10-09 — Checkpoints never commit a file over 50 MB, and commit nothing if one checkpoint would add over 200 MB** — a blanket `git add -A` once swept ~1.2 GB of unwanted files (mostly 30 MB PDFs) into a repo's history. Single files over `CHECKPOINT_MAX_FILE_BYTES` (default 50 MB) that are untracked, modified or already staged are left out of the commit (unstaged if needed), stay on disk, and are listed in `.claude/.last_checkpoint_sync_problem`. If the remaining pending changes total more than `CHECKPOINT_MAX_TOTAL_BYTES` (default 200 MB), the working tree is not committed at all, because the per-file limit alone does not stop a folder of many mid-size files. Symlinks count as links, not their target. Tested: 60 MB untracked, 55 MB modified, staged big file, symlinks, 4 x 30 MB folder over a 100 MB test cap, plus bash 3.2.
